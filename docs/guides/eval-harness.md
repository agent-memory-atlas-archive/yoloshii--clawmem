# Offline eval harness

Measure retrieval quality against a hand-labeled gold set instead of eyeballing it. `clawmem eval run` replays labeled queries through the **real** `query` tool handler — the exact code path an agent's MCP call takes, including expansion, RRF fusion, rerank blending, composite scoring, and MMR diversity at their tool defaults — and scores the returned documents against gold evidence with doc-level Jaccard (`J = |C∩E| / |C∪E|`), precision@k, recall@k, hit@k, and MRR. It exists so ranking/extraction changes ship **measured**: a before/after pair of runs on the same gold set is the evidence a change actually helps.

The harness is offline and CLI-only (no MCP tool). The replayed path writes nothing to `context_usage`, `recall_events`, or `memory_relations` — eval runs never contaminate the retrieval, lifecycle, or telemetry state they may later mine for label candidates. It is not byte-level read-only, though: expansion and reranking may populate the normal inference cache (`llm_cache`), exactly as any live query would.

## Gold files

Gold sets are versioned JSONL files that live **outside** the vault DB — pass any path via `--gold`, so private labels can stay out of the repo. One example per line:

```json
{
  "id": "p1-why-001",
  "query": "why did we defer FastRP?",
  "mode": "query",
  "include_internal": true,
  "gold_evidence": [
    { "collection": "_clawmem", "path": "decisions/2026-06-12-context-graph.md" }
  ],
  "tags": ["why", "decision"]
}
```

| Field | Required | Notes |
|---|---|---|
| `id` | yes | Unique per file — duplicates are a hard error. |
| `query` | yes | The query to replay, verbatim. |
| `mode` | no (default `query`) | Which replay surface the example is labeled for: `query` \| `intent_search` \| `context` \| `raw` \| `structured`. A run replays only the examples matching its `--profile`; the rest are skipped with accounting. |
| `include_internal` | no (default `false`) | Passed through to the tool call. Gold evidence in `_clawmem` needs `true` — retrieval tools exclude internal docs by default. |
| `collection` | no | Optional collection filter passed through to the tool call. |
| `gold_evidence[]` | yes (≥1) | Each ref needs `collection` + `path`. Optional: `hash` (content pin — a mismatch warns that the label may be stale, but still scores), `weight`, `span`, `chunk_seq` (parsed and carried; scoring is doc-level in this build, so they do not affect metrics — weighted/nDCG variants are a later phase). |
| `force_intent`, `budget_tokens` | no | Knobs for the `intent_search`/`context` replay profiles (follow-on phases); carried, unused by the `query` profile. |
| `gold_answer` | no | Answer rubric for optional offline answer scoring (not implemented; retrieval gold only). |
| `tags[]` | no | Aggregated into a per-tag metrics table in the report. |

**Labeling discipline:** the hand-labeled file is the authority — telemetry ("the assistant referenced this doc") proposes candidates but is never truth. 30 resolved examples is a feature-specific smoke floor; 80–120 gives a trustworthy global number. Hand-audit 10–20% of labels, then attest it with `--audited` — the trust gate requires the attestation (the harness records it; it cannot verify it).

**Strictness:** any malformed line, schema violation, unknown field (a typo like `includeInternal` would otherwise silently evaluate a different route), or duplicate id fails the whole load — a silently dropped example would corrupt the metric. Repeated tags are deduplicated. An example with **any** evidence ref that doesn't resolve to an active document is excluded from scoring entirely — partial gold would silently inflate recall — and fails the run's trust gate *regardless of the example's `mode`* (a stale label never vanishes into the skipped list).

## Running

```bash
clawmem eval run --gold labels.jsonl                      # profile query, k=10, out to ./eval-runs/<run_id>/
clawmem eval run --gold labels.jsonl --limit 5 --out runs/baseline
clawmem eval run --gold labels.jsonl --min-examples 80 --audited   # global-number trust floor, audit attested
clawmem eval run --gold labels.jsonl --audited --db snapshot.sqlite   # corpus-frozen run against a DB snapshot
clawmem eval run --gold labels.jsonl --json               # print run.json to stdout
```

| Flag | Default | Meaning |
|---|---|---|
| `--gold <file>` | required | Gold JSONL path. |
| `--profile query` | `query` | Replay surface. This build implements `query`; `intent`/`context`/`raw`/`structured` are follow-on phases. |
| `--limit N` | 10 | The k in the @k metrics — the `limit` passed to the replayed tool. |
| `--min-examples N` | 30 | Trust-gate floor for `examples_scored`. |
| `--audited` | off | Attest that a 10–20% hand-audit of the gold labels passed. Recorded as `audit_attested` in `run.json`; the trust gate fails without it. |
| `--out <dir>` | `eval-runs/<run_id>/` | Where `run.json` + `report.md` land. |
| `--db <path>` | live vault | Point the whole run (resolution + replay) at a snapshot DB — e.g. a `VACUUM INTO` copy. Corpus-frozen (documents and labels can't drift between runs), not fully deterministic — the snapshot is opened writable and inference caches may populate, and live expansion/rerank services can still vary. Must already exist (a typo'd path is refused, never created as an empty vault). |
| `--json` | off | Emit `run.json` to stdout instead of the summary line. |

Run it via `bin/clawmem` as usual so the inference endpoints are set — the replay uses whatever embedding/expansion/reranker services the live pipeline would. **Exit code:** `0` only when the run completes AND the trust gate passes; a completed run with a failing gate exits `1` (artifacts still written) so automation can never mistake an untrusted number for a trusted one.

**Identity integrity:** retrieved results are mapped back to document ids by inverting the `collection/path` display path. If a returned path maps to zero documents (vault changed mid-run) or to more than one (a collection name containing `/` colliding with a sibling — nothing forbids such names), the run hard-fails rather than guess or silently drop the result, since either would corrupt precision and Jaccard.

## Reading the output

`run.json` is the machine artifact: run metadata (profile, k, gold path, DB path, clawmem version), `aggregate` (jaccard/recall/precision means, hit@k, MRR, p95 latency), `by_tag` slices, per-example detail (metrics, retrieved vs gold doc lists, warnings), `unresolved_gold`, `skipped`, and `gates`. `report.md` is the human companion for hand-auditing.

Token-axis fields (`tokens_mean`, `recall_per_1k_tokens`) are `null` under the `query` profile — the only honest token measure is the context-surfacing replay's `buildContext` accounting, which lives in the hook replay's per-case trace (`clawmem eval hook-run`, below).

**Gates in this build are the labeled-set trust gate only**: enough scored examples, zero unresolved refs, and the `--audited` operator attestation. Comparative feature gates (e.g. "recall must improve ≥5pp with no >10% token increase") are computed *between* runs — do an A/B by running the same gold file against two checkouts or two `--db` snapshots and comparing the two `run.json` artifacts.

## Hook replay (`clawmem eval hook-run`)

The context-surfacing hook is a different surface from the `query` tool — multi-turn lookback, several retrieval legs, deep escalation, adaptive admission — so it has its own replay: `clawmem eval hook-run` drives labeled UserPromptSubmit cases through the **real** `contextSurfacing` handler against a corpus snapshot (`--db` is required; make one with `sqlite3 ~/.cache/clawmem/index.sqlite "VACUUM INTO 'snap.sqlite'"`). Each case freezes `{prompt, prior turns (seeded so the real lookback runs), profile}` plus judged labels: per-document `must_include` / `acceptable` / `must_not_include`, the prior-leg decision (`required` / `harmless` / `forbidden`), `expect_abstain`, and a `split` (`tuning` / `holdout`). Expansion outputs are regenerated by the live pipeline per input shape, never replayed from stale concatenated queries.

One case per JSONL line:

```json
{
  "id": "hk-001",
  "prompt": "Can you explain that rationale in more depth",
  "priors": [{ "text": "the OAuth refresh token rotation decision", "age_minutes": 2 }],
  "profile": "balanced",
  "prior_leg": "required",
  "labels": { "must_include": ["notes/oauth-decision.md"], "must_not_include": ["research/seo-hacks.md"] },
  "split": "tuning",
  "tags": ["multi-turn"]
}
```

Metrics: graded nDCG@k over the injected order, must-not-include rate (case- and doc-level), must-include recall, abstention accuracy, false-abstain rate, prior-leg decision accuracy, latency p50/p95, and whole-hook timeout rate (`--budget-ms`, default 8000) — reported overall and per split. Every case is also audited against the **hermetic invariant registry** (`src/eval/hook-invariants.ts`): enforced invariants fail the run's gate (trace completeness and admission honored since BUILD-0; the expansion mass cap and the failed-rerank expansion-leak guard since BUILD-1; the single channel-aware ranking key since BUILD-2); unenforced ones measure the standing ranking defect and are reported as observed violations until the build that fixes each flips its flag.

**Acceptance gate (`--baseline <hook-run.json>`):** a candidate change is judged against a prior run on the **held-out slice only** — there is no overall-aggregate fallback; a missing holdout slice on either side fails acceptance. Axes: nDCG, must-include recall, abstention accuracy, and prior-leg accuracy may not regress beyond a small tolerance; must-not case rate and timeout rate may not increase (timeouts must be 0); p50/p95 latency may not regress beyond a relative+absolute margin. An axis measured on only one side fails closed. An axis whose **label stratum is empty on the held-out slice** (e.g. no `must_not_include` labels — a zero damage rate would be indistinguishable from no coverage) is forced UNMEASURED, and an unmeasured axis **fails acceptance unless explicitly declared out of scope** with `--accept-unmeasured <axis,...>` — a machine-visible declaration recorded in the acceptance notes, never a silent skip. Only the **waivable** axes (abstention, prior-leg, latency p50/p95) accept a declaration; the core relevance and damage axes (nDCG, must-include recall, must-not rate, timeouts) are **non-waivable** — a holdout that cannot measure them is not an acceptance set. Any honored waiver makes the result a **conditional** pass (`acceptance.mode: "conditional"`, `gates.acceptance_waived`): `gates.pass` (unconditional product acceptance) stays false, while the CLI exits 0 because the waiver was the invocation's own explicit instruction.

**Run identity:** every report embeds an identity fingerprint — a sha256 over the canonicalized **full scored gold cases** (the label-resolved, cleaned examples: prompts, priors, labels, rulings — not just ids), the **content hash of the working copies actually executed** (length-framed per file, so no concatenation ambiguity and no gap between what was hashed and what ran), the inference topology (endpoint URLs; the **effective** model ids — embed/query honor the `CLAWMEM_EMBED_MODEL`/`CLAWMEM_LLM_MODEL` env overrides, while the rerank model records the hook's store constant because no `CLAWMEM_RERANK_MODEL` override is honored by the runtime; LLM reasoning-effort/no-think options; and served-model probes — `/v1/models` for embed/llm, a fixed-input **behavioral score fingerprint** for the rerank sidecar), limit, budget, profiles, and the latency protocol. LLM options record what the runtime **executes**, not the raw env: an unset `CLAWMEM_LLM_NO_THINK` records `"true"` (the constructor default), so unset and every affirmative spelling fingerprint identically; an unsupported reasoning effort records `"default"`. Served probes are tri-state: a value, `unreachable` (endpoint down — itself an identity-relevant topology state), or `unknown` (endpoint answered but unfingerprintable) — an `unknown` on a service the run's profiles exercise fails comparability unless that identity is attested. `--baseline` refuses to compare when identities differ. A baseline **without** an identity is an informational comparator only — its axes are reported but `acceptance_pass` can never be true against it; a baseline produced before identity fingerprints existed can be attested through `scripts/eval-hook-stamp-baseline.ts` (resolves and cleans the gold labels against working copies of the attested snapshot exactly as a live run does, verifies the report's cases, records the invoker-attested topology, and marks the identity `attested` so it is never mistaken for run-time-recorded).

**Local-fallback policy:** the eval CLI forces `CLAWMEM_NO_LOCAL_MODELS=true` for its runs unconditionally (the ambient value is launcher policy, not an invoker decision), because with local fallback allowed, an endpoint that fails **mid-run** silently swaps in an unidentified in-process model while the identity keeps the healthy preflight probe. `--allow-local-fallback` opts out for **trust-only exploration runs**; the executed policy is recorded as `topology.local_fallback`. Acceptance comparison **forbids** an allowed-fallback candidate outright. An allowed-fallback **baseline** must be attested and compares by policy, not blind equality: `fallback_observed: "none"` (route evidence proves no local model executed — pipeline-equivalent to blocked) is fully comparable; `"unknown"` (the routing cannot be reconstructed) demotes the comparison to **informational-only** — axes are computed and reported but acceptance can never pass; unattested-allowed refuses to compare at all. The stamp tool requires `--fallback-observed none|unknown` whenever it attests an allowed policy, and truthfulness is the point: attesting `blocked` for a run that executed under the launcher's default `allowed` would attest a policy the run never executed.

**Paired counterfactuals and the pair gate (`--pair-with`):** a ranking-policy A/B is only evidence when both arms ranked *identical inputs*. Two protections cover that. First, `--capture-expansions` / `--replay-expansions` freeze one arm's expansion draw and replay it into the other, and the draw file carries a **binding** validated against the replaying run: gold fingerprint, corpus content hash, query/rerank models, the rerank **request-construction revision**, the **served-provider fingerprint** of the reranker (cached scores are that provider's outputs), and a **transmitted-text manifest** — a hash over the exact texts the reranker was sent. A mismatch on any member refuses the run and tells you to re-capture; a draw file from an older build is refused by shape.

Second, `--pair-with <partner-run-dir> --pair-min-valid N` audits the two arms **per case** after the run: every pre-treatment surface (retrieval query, expansion state, raw candidates with their channel scores, the whole fusion envelope, rerank coverage, and the hashes of the text actually transmitted to the reranker) must match the partner's, using the same comparison the standalone `bun src/eval/pair-audit.ts <dirA> <dirB>` applies. A case that diverges is **re-run fresh** (up to `--pair-max-retries`, default 2) — a transient dropout deserves a replacement replicate, not a poisoned mean — and one that still diverges is **excluded**. Consequences worth knowing before you read the numbers:

- every aggregate in a pair-gated report covers **valid pairs only**; rejected cases stay in `cases[]` with `pair_valid: false` and are listed in `pair_audit`;
- acceptance recomputes **both** sides over the same valid ids, so `--baseline` must be the partner's own report;
- fewer than `--pair-min-valid` valid pairs **refuses the run** (the count is pre-registered — a threshold picked after seeing the audit is not a gate), and the refusal carries the diverging cases as evidence;
- a pair-gated report is refused as a `--baseline` for an ungated run, since its means cover a different case set.

A total valid-pair count is not by itself the experiment: an arm could discard every treatment-bearing case and still meet it on cases where the treatment is inactive. Pre-register the cases that must survive — `--pair-require-ids <a,b>` (named witnesses) and `--pair-min-valid-stratum <deep=8,holdout=6>` (per-profile and per-split minimums) — and the gate refuses the run when a witness or a stratum is lost, naming what diverged. Topology coverage is registrable the same way: `--pair-min-basis-stratum <stratum>:<basis>=<n>` (e.g. `speed:bm25-rrf=3`) counts VALID pairs whose case was judged on the named admission basis, records both the minima (`min_basis_by_stratum`) and the coverage (`valid_basis_by_stratum`, derived from the case rows' `admission_basis` and ledger-reconciled) in the pair protocol, refuses the run when unmet, and is re-verified by the replicated aggregate as a conjunct of `gates.pass` — the machine-decisive form of a topology-complete shipping requirement.

Being a valid pair is not the same as having *exercised* the treatment: two arms that both timed out before reranking pair perfectly while the ranking policy never ran. The **base exposure** predicate — the pre-treatment *reach* predicate of the registered treatment family: the rerank lane answered completely with at least two candidates to reorder (rerank-lane treatments and the no-treatment replicate audit), a nonempty admission-input ledger reached the policy branch (`admission_policy`), every family's reach for a confounded registration — is what named `--pair-require-ids` witnesses must meet (they are regression-watch cases: they must have *reached* the policy, whatever the treatment). `--pair-min-exposed-stratum <deep=6>` states a minimum counted over **treatment-aware** exposed pairs only — under a registered `degeneracy_gate` treatment that additionally requires the assessment to have fired — so a `deep` minimum cannot be satisfied by degraded RRF cases, nor by cases the gate treatment never touched. The report records `treatment_exposed` alongside the valid count. Both are validated up front: an id absent from the gold set, or a stratum matching neither a profile nor a split in it, is refused before any case runs.

**Registered treatments (`--pair-treatment`):** three ranking-policy variables are *registrable* as the difference between the arms of a pair — the rerank-lane weight (`CLAWMEM_RERANK_LANE_WEIGHT`), the degeneracy-gate toggle (`CLAWMEM_RERANK_DEGENERACY_GATE`), and the admission policy (`CLAWMEM_ADMISSION_POLICY` — `relevance` is the v0.38.0 product default; `composite` is the prior composite gate kept only as a control arm) — all recorded in the run identity. The registration is the contract: `--pair-treatment degeneracy_gate` permits exactly that difference in the in-run identity gate *and* in paired acceptance (where `--baseline` is the partner by construction, the registered difference is what the experiment measures); everything else must match, an *unregistered* treatment difference refuses the pair, and omitting the flag demands policy-identical arms (a replicate audit). The *unpaired* `--baseline` path stays strict — it never accepts a treatment difference. Registering both treatments at once is possible but declares a confounded two-factor experiment; the post-hoc audit likewise refuses a two-factor pair unless explicitly told to compare it. Exposure is treatment-aware: under a `degeneracy_gate` registration, `--pair-min-exposed-stratum` counts only pairs whose score set actually *fired* the gate (a never-degenerate case executed identically in both arms), while `--pair-require-ids` witnesses remain regression-watch cases judged on the base predicate — the lane answered completely with candidates to reorder. The gate's *assessment* runs in both arms regardless of the toggle — a gate-off control arm still traces how often the gate would have fired — so the toggle changes only whether a degenerate lane is discarded. Under an `admission_policy` registration, exposure and pairing both read the **admission-input ledger** (`admissionInput` in the trace — recorded immediately *before* the policy branch, arm-symmetric by construction; each entry carries the complete per-candidate policy input of both arms: the ordering key `{band, mass}` the relevance policy judges and the `compositeScore` the composite control judges): a case is treatment-exposed iff a nonempty candidate set reached the branch, and an **admission-only** pair (no rerank-lane treatment registered alongside) is valid only when the ledgers match entry-for-entry — the admitted/rejected *split* is produced by the selected policy arm and is never consulted, and a malformed ledger refuses rather than coerces. A registration combining `admission_policy` with a rerank-lane treatment skips the ledger comparison: the upstream treatment legitimately changes the failure guard and therefore the admission input, so differing ledgers are part of the declared (confounded) combined treatment. Composite policy inputs are deterministic across arms only on a shared clock: the A/B runner pins `CLAWMEM_EVAL_NOW` identically on both arms (canonical ISO-8601 UTC only — a present-but-invalid value refuses the run before scoring rather than silently falling open to wall time), the identity records it as `eval_now` (null = explicit wall clock), and a clock mismatch — or a pre-turn-55 identity with no recorded clock — refuses on *every* comparison surface: the pair gate (absent-on-either-side included — two unidentified legacy clocks are not equal clocks), unpaired acceptance, and replicated-member aggregation (it is not a registrable treatment). Across a replicated experiment the pin is *experiment-level*: `scripts/experiment-clock.sh` persists one clock per experiment dir (`EVAL_NOW` file) so separately launched draw invocations share it — a conflicting explicit value refuses instead of silently forking the clock, initialization is atomic (O_EXCL — concurrent first launches cannot fork it, and the exported value is always the durable file's), and an empty or corrupt pin refuses rather than reseeding; delete the file to start a new experiment.

**Replicated draws (`eval hook-aggregate`):** expansion sampling is a first-order noise source on deep behavior, so a single-draw deep comparison is a point estimate of a distribution. The replicated-distribution protocol runs the paired experiment *n* times — each draw captured once (`--capture-expansions`, on the control arm) and replayed into the candidate arm, each candidate run pair-gated and acceptance-compared against its partner draw — and then aggregates the *n* **candidate (paired) run directories only**. The capture arm cannot itself be pair-gated (capture and pairing are mutually exclusive), and its side of the evidence already rides the candidate runs' acceptance axes as the baseline values:

```bash
clawmem eval hook-aggregate --runs runs/d1,runs/d2,runs/d3 --out runs/aggregate
```

The aggregate validates every member field it consumes at baseline grade (a report whose gates disagree with its own acceptance block, or whose acceptance baseline is not its pair partner, is refused as not written by this code) and refuses structural impossibilities (a member that is not a frozen draw, two members sharing one draw, any identity difference between members, mixed pair/acceptance presence, an unidentifiable pipeline). Otherwise it reports per-draw trust/acceptance verdicts plus per-axis distributional summaries — per-draw values, means, the candidate range, the mean delta, and whether the delta's **direction is stable across draws** (the machine form of "only cross-draw-stable conclusions are claimed"). Its identity is stamped `expansion_set: "replicated:<n>"` with the sorted per-draw fingerprint list itemized, so a distributional claim is auditable draw by draw. (The identity comparison rule accepts replicated-vs-replicated at equal *n*, but no aggregate-vs-aggregate acceptance flow exists yet — the paired per-draw form is the acceptance surface; treat the aggregate-level comparison as future machinery, not a reachable acceptance path.) The aggregate's own gate passes only when every draw's trust gate passed, every draw's acceptance passed, **every draw was pair-gated** (unpaired per-draw acceptances are not paired evidence), and no draw was conditional — a waived axis on one draw never aggregates into an unconditional distributional pass. For shipping acceptance use at least **five** draws; three is a pilot.

**Latency protocol:** each case is replayed `--latency-reps` times (default 3) — every rep under its own fully-isolated replay session — and the case latency is the lower median (single-run replay latency is machine-state noise; reps share the expansion cache by design, so the protocol measures warm-expansion latency, stable across A/B runs on one snapshot). The protocol is part of the run identity: a baseline measured under a different protocol makes the latency axes unmeasured (declare them or re-baseline), never silently comparable.

**Vector execution protocol (`--vector-exec`, default `daemon-required`):** the handler's vector timeout is a `Promise.race` timer on the hook's own event loop, and the sqlite-vec MATCH is synchronous — so on a daemon-less working copy the timer *cannot fire* and a cold scan blocks the handler for its full duration (an execution production never performs under the watcher; a draw of the v0.38.0 ship run refused its budget gate on exactly that artifact). `hook-run` therefore executes the daemon-backed topology: before the first case it spawns a dedicated **vector-daemon child** on the working copy (the production `startVectorDaemon`; no watcher, no indexing), waits for bounded *verified* readiness (a ping round trip must name the working copy and the child's own pid — a foreign daemon on the socket refuses), runs **every** vector leg daemon-required (a stale or missing daemon returns nothing and the run is refused as daemon loss — never the in-process scan), and in `finally` terminates the child with a bounded escalation to SIGKILL and removes its socket before the working directory goes. `--vector-prewarm steady-state` (default) runs the watcher topology's periodic prewarm before readiness and records it; `cold` skips it. The protocol is **identity** (`vector_exec: { protocol, prewarm, response_protocol }`): strict across `--baseline`, the pair gate (refused in preflight) and replicated members, never a registrable treatment, and a pre-t76 report without it fails closed on every comparison surface. `response_protocol` names WHICH response execution the daemon legs measured — `"hydrated-v1"` (v0.38: daemon-side hydration + projection, zero synchronous sqlite on the hook's timed path) vs `"raw-hit"` (raw hits + synchronous client-side hydration, the pre-v0.38 execution) — and a daemon-required report without it (pre-t84) likewise fails closed, which is what quarantines raw-hit members from a hydrated rerun. The runner enforces the recorded value at runtime: the child's readiness ping must attest `hydrated-v1` in its advertised protocols, a hydrated leg answered with raw hits is classified `skew` (never hydrated client-side) and refuses the run like daemon loss, and an ok leg served raw hits refuses it too (defense in depth). Ownership is verified **around every rep**, not only at startup: before and after each rep the daemon must answer a ping naming the exact working copy and the child's own pid (a daemon killed mid-request, a listener that vanished while the pid lives, or a socket taken over by another daemon all refuse the run; a `busy`/`error` leg is an ordinary bounded fallback only when that check passes — and because the child is single-threaded, every rep also starts on an idle daemon). The ownership bound is a fixed 30s constant (`OWNERSHIP_PING_TIMEOUT_MS`), part of the protocol rather than a per-run variable. `steady-state` is a claim that a vector payload was warmed: on vector-exercising profiles a prewarm with nothing to warm (no dimensioned vector table, or a dimensioned table with zero stored vectors) refuses the run rather than measuring the FTS fallback under a daemon-backed identity; speed-only runs are vacuous and record `prewarm_ran: false` honestly. `--vector-exec in-process` is the recorded opt-out: the legs run the in-process scan, `vector_exec.latency_authoritative` is `false` on vector-exercising profiles, the latency acceptance axes are unmeasured (waivable only by explicit declaration), and the handler **budget gate is unmeasured too** — `gates.budget_elapsed_ok` is `null`, trust fails as "budget evidence UNMEASURED" (never as a production-looking pass or overrun), and the raw timing stays in `budget_elapsed` as a diagnostic. Direct `runHookEval` callers declare `vectorExec`; an in-memory store implies in-process (a child cannot serve it), a file-backed store must declare or is refused. The evaluator's environment is a transaction: every refusal path (preflight or mid-run) restores the mutated env and clears the config cache. The **deployed** vault is a separate, enforced prerequisite: the latency contract holds for daemon-backed deployments, so `clawmem doctor` checks the watcher's daemon by a real round trip and `clawmem vec-daemon-health` is what a shipping preflight gates on — a socket file is not a listener. Exit 0 is reserved for the Path-A-AUTHORITATIVE state (`live`: exact DB/pid attested AND both `hydrated-v1` and `deadline-rel-v1` advertised); `live-raw` (attested but missing either — the v0.38 hook classifies its answers `skew` and falls back to FTS) and `live-legacy` (a pre-v0.38 watcher that cannot attest) prove liveness only and exit 1. A v0.38 shipping preflight additionally requires the ATTESTED form with BOTH `"hydrated-v1"` and `"deadline-rel-v1"` in the advertised `protocols` (the JSON output carries them): `live-legacy` proves a listener, but a pre-v0.38 watcher cannot serve the v0.38 hook (its answers are `skew`, so production vector legs fall back to FTS) — not the contract a hydrated-v1 run certifies — and a daemon without `deadline-rel-v1` ignores the relative budget the O1 wire carries. **Deadline protocol (O1, v0.38.0):** every run also records the top-level identity `deadline_protocol: "monotonic-relative-v1"` — the handler's deadlines derive from one monotonic anchor, the daemon wire carries a relative remaining budget, and the per-leg `over_ms` is monotonic. It is strict across `--baseline`, the pair gate (preflight) and replicated members and never a treatment; a report without it measured wall-clock deadline semantics and fails closed everywhere. The runner refuses a daemon child whose readiness ping does not attest `deadline-rel-v1`, and a leg the daemon answered without that attestation (`skew`) refuses the run like daemon loss. Every rep's per-leg timing record is persisted in `hook-run.json` as `vector_leg_records` (keyed `case` + `attempt` + `rep` — a pair-gate retry re-scores a case under a new attempt, and every attempt's legs stay evidence: `over_ms`, `budget_ms`, `mono_elapsed_ms`, `wall_elapsed_ms`, `clock_skew_ms` — a realtime step visible from the artifact — `terminal_kind` × `status`, and `timing` = `early` / `on_time` / `late` against the frozen 150 ms tolerance).

The report's gate is machine-split: `gates.trust_pass` (the run's own trust/invariant gate), `gates.acceptance_pass` (`null` without a baseline — never a pass), and `gates.pass` (product acceptance: both). Exit code follows what was asked: the trust gate without `--baseline`, product acceptance with it.

Artifacts: `hook-run.json`, `report.md`, and `traces.jsonl` — one full per-stage provenance trace per case (legs, per-candidate raw channel scores, rerank coverage, composite scores, admission decision, final order). The same envelope can be captured live: `CLAWMEM_SURFACING_TRACE=1` makes the hook persist traces into the `surfacing_diagnostics` table (newest 500 kept) for post-hoc ranking diagnosis. Caveat: this live capture performs a synchronous SQLite write on the hook path *after* both clocks stop — it is excluded from `finalizationMs`, the finalization reserve, and the handler-budget accounting — so it adds real wall-time the hook's own gates cannot see. Treat it as a diagnostic mode: leave it off during latency measurement or timing-sensitive eval runs. Since v0.38.0, `finalizationMs` (what the finalization-reserve gate bounds) measures escalation-end → *payload assembled* — output-critical construction only, because the injection bookkeeping left the handler entirely: the alignment/query-history `context_usage` row is written early at retrieval commit (so turn alignment and prior-turn lookback survive a deadline-skip), while the paths/tokens fill-in, recall events, and per-vault mirror are handed off after the payload boundary to a detached `clawmem spool-ingest` child via an on-disk spool (`clawmem spool-drain` is the manual recovery drain). `postOutputMs` measures the in-handler handoff (recorded for every payload-bearing profile), and `postOutputSkipped` marks the deadline-passed case where even the handoff is skipped.

Isolation: the run disables the prompt-dedup gate, seeds and deletes its own per-case session telemetry, restores `co_activations` after every case, and suppresses secondary-vault surfacing unless `--skill-db` points the secondary lane at its own snapshot. Draft cases can be mined from real history with `bun scripts/eval-hook-capture.ts --db snap.sqlite --out drafts.jsonl` — drafts carry TODO markers the strict loader refuses until a human triages the labels.

## Relation to `scripts/eval-*.ts`

The route-local scripts (`eval-keyword-acceptance.ts` etc.) are **frozen decision bundles**: they mirror specific handler internals deterministically for one A/B verdict, run FTS-only with zero services, and stay untouched as historical artifacts. This harness is the general product surface — it replays the real handlers end-to-end rather than mirroring them, so it measures the product, not a copy that can drift.
